# V3.18 V3.16-log audit and correction

## Terminal result

The complete V3.16 build log contains 48,355 lines. The first causal failure occurs during final target-root customization, after the long native builds and Armbian image construction:

```text
libSDL2_ttf-2.0.so.0 => not found
libQt6QuickControls2.so.6 => not found
Moonlight has unresolved shared libraries
```

The failure is not a Moonlight compile or link failure. The isolated ARM64 Moonlight build installed both `libsdl2-ttf-2.0-0` and `libqt6quickcontrols2-6`, compiled the pinned source, linked the executable to the dedicated V4L2 Request FFmpeg libraries and packaged the launcher. The corresponding runtime packages were absent only in the assembled target root filesystem.

## Cause

Moonlight's artifact recipe listed the QML modules but did not explicitly list the SDL2_ttf or Qt Quick Controls shared-library packages. Generic runtime-package discovery asks `ldd` for library paths and then asks `dpkg-query -S` which package owns each path. On merged-`/usr` systems, `ldd` may report `/lib/aarch64-linux-gnu/...` while dpkg records `/usr/lib/aarch64-linux-gnu/...`; an exact lookup can therefore return no owner even though the package is installed in the build container.

Most other libraries arrived transitively through the base image packages. These two did not, exposing the collector weakness. The target-root `ldd` gate worked correctly by stopping the build rather than producing a broken image.

## V3.18 correction

- `libsdl2-ttf-2.0-0` and `libqt6quickcontrols2-6` are explicit base runtime packages, so the early Ubuntu Resolute ARM64 solver validates them before long compilation.
- Moonlight's artifact runtime manifest independently records both packages.
- The shared collector now retries dpkg ownership lookup using `readlink -f` canonical paths, addressing the merged-`/usr` failure class for every native artifact.
- The final target-root gate checks package installation, zero unresolved Moonlight dependencies, and affirmative resolution of both libraries.
- Offline image QA requires both shared-library files in the completed image.
- Static checks protect every layer of the correction.

## Other log findings

The numerous CMake `not found` and feature-test `Failed` lines are platform/optional capability probes, not fatal errors. Azahar reported `100% tests passed, 0 tests failed out of 64`; five hardware-dependent audio/DSP tests were explicitly skipped rather than failed. Armbian's first two attempts to resolve the U-Boot tag used branch-shaped ref names and failed, then its correct `v2025.10^{}` lookup resolved commit `e50b1e8715011def8aff1588081a2649a2c6cd47` and the cached U-Boot artifact was accepted. The missing Docker buildx plugin only forced a slower local builder-image rebuild.

The two `sudo: unable to resolve host` messages occurred inside the transient Armbian customization chroot and did not stop their commands. The `COLUMNS` notices, suppressed service starts, desktop-category hint and optional developer/architecture probes are also non-causal. No compiler, source-pin, Stremio, emulator, kernel or image-construction failure precedes the Moonlight target-root gate.

V3.16 produced no distributable image because customization failed before offline image QA and final copying. V3.18 must start from a completely fresh workspace. Static proof cannot replace the full host build or physical Orange Pi hardware validation.
