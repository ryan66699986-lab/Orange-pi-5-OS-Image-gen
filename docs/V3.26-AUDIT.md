# V3.26 scope and maintenance audit

## Decision outcome

V3.26 implements the user's clarified product and workflow intent without removing the existing emulator catalogue or hard media/controller gates. The target is a personal Orange Pi 5 Pro appliance, while avoiding machine-specific assumptions that would prevent the same image from working on another Orange Pi 5 Pro.

The project is intentionally not expanded with a tiling compositor or an X11-first desktop. ES-DE remains the controller shell, Gamescope remains preferred, and Labwc remains the only desktop/recovery compositor. Both Brave and Firefox remain installed. Steam remains visible and experimental. Testing stays entirely on SD; after final approval root moves to Btrfs NVMe while boot stays on SD, and later boot moves to eMMC while NVMe remains root.

## Build persistence correction

The earlier phrase “fresh workspace” protected against stale userpatches, partially installed root filesystems and broken application outputs. It did not require re-downloading immutable Armbian Git history.

V3.26 therefore persists `~/.cache/opi5pro-builder/git/armbian-build.git` as a bare source mirror. Every use verifies the official origin, performs a bounded remote update and runs Git connectivity checking. The selected main commit is then copied with `--no-local --no-hardlinks` into a new detached versioned checkout. The build checks that checkout is at the selected commit and initially clean. Userpatches, rootfs state, native builds, merged overlay and image output remain disposable and are never resumed after failure.

## Session refinement

The existing V3.25 wrapper already preferred Gamescope and entered Labwc after exit. V3.26 makes the recovery distinction explicit:

- normal Gamescope/ES-DE exit enters the Labwc desktop;
- a nonzero Gamescope failure launches ES-DE directly under Labwc;
- `direct-gaming-mode` permits intentional A/B testing without Gamescope;
- Gamescope remains a required final test, so recovery success cannot conceal its failure.

## Component policy

| Tier | Meaning | Components |
|---|---|---|
| Core | Failure rejects even an MVP candidate | Boot/graphics/session recovery, controller/OSK, native Stremio hardware decode, Moonlight, network and audio |
| Required | May be diagnosed after first boot; must pass before final | Gamescope, every declared emulator, Firefox, CEC and removable storage |
| Experimental | Visible evidence only; non-blocking | Steam ARM64 and GE-Proton |

The builder still requires and packages the entire specified emulator set because previous full logs proved all ten native artifact builds and the distro emulator packages reached target assembly. The tiers change operational interpretation, not artifact completeness.

## Update boundary

`opi-update` implements rolling maintenance within Ubuntu Resolute:

1. require root, ARM64, Orange Pi 5 Pro and Ubuntu Resolute;
2. serialize through `/run/lock/opi-update.lock`;
3. run core appliance health;
4. refresh signed APT metadata and simulate `apt-get upgrade`;
5. show image-managed pinned versions separately;
6. refuse apply while gaming/media/browser processes are active;
7. require 1.5 GiB free and literal `UPDATE` confirmation;
8. record installed package versions before and after;
9. use `apt-get upgrade`, which does not remove installed packages;
10. audit dpkg and rerun core health; never reboot automatically.

Security-only unattended upgrades remain enabled. Manual maintenance covers same-release Armbian kernel/firmware/BSP, Ubuntu packages, Brave, Firefox and distro-packaged emulators. `/etc/update-manager/release-upgrades` is fixed to `Prompt=never`, and static/target/offline gates reject `dist-upgrade`, `full-upgrade` or `do-release-upgrade` in the updater.

Source-built Stremio, dedicated FFmpeg/mpv, Moonlight and source-built emulators are deliberately not called rolling. Their exact versions remain in `/opt/opi-build-meta/versions.lock.json`; a future signed project-bundle channel must build them externally and repeat architecture, runtime-closure and hardware acceptance before on-device replacement.

## Static evidence and remaining proof

Repository validation covers shell syntax for every generated helper, sorted package manifests, mirror isolation, direct-session selection/fallback, component tier presence, updater safeguards, forbidden release-upgrade commands, target-root requirements and completed-image requirements. All pre-existing Stremio, Moonlight, controller, emulator, graphics, browser, firmware, filesystem and read-only NVMe gates remain.

Still unproven until a fresh V3.26 build and physical test:

- mirror creation/hit behavior on the user's Docker host;
- Gamescope-failure transition and deliberate Direct Gaming Mode;
- real same-release update with package-version records and post-update health;
- all existing boot, PanVK, controller, media, emulator, network/audio and storage hardware gates.
