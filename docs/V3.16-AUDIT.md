# V3.16 intensive audit

## V3.15 build evidence

The complete V3.15 log was reviewed through its terminal command, not only its final lines. All host, Docker, loop-device, ARM64 execution, source-resolution, Ubuntu Resolute package, browser, Armbian edge and Linux 7.1 media/kernel preflights passed.

The run completed Snes9x 1.63, native Stremio 1.1.4 with the dedicated V4L2 Request FFmpeg/mpv stack, PPSSPP, ES-DE 3.4.1 and gamepad-osk. This proves the V3.15 Snes9x compatibility patch and retains the earlier native Stremio build proof.

Moonlight 6.1.0 then compiled and linked its ARM64 executable. Before packaging, the recipe proved all of the following:

- `app/moonlight` existed and was executable;
- the ELF contained `/opt/opi/media/lib` in RPATH/RUNPATH;
- `ldd` reported no unresolved libraries;
- `libavcodec`, `libavutil` and `libswscale` resolved from the dedicated project media prefix;
- the binary contained the affirmative hardware-versus-software decoder evidence string.

The deterministic stop was line 110 of the generated Moonlight recipe:

```text
/build.sh: line 110: /out/rootfs/usr/local/bin/moonlight-qt: No such file or directory
```

The preceding `install -D` created `/out/rootfs/opt/opi/apps/moonlight`, not `/out/rootfs/usr/local/bin`. Shell redirection cannot create parent directories. This was therefore a packaging precondition omission after a successful compile, not a source, ABI, media-stack, ARM64 or hardware-decoder build failure.

## V3.16 correction

The recipe now explicitly creates `/out/rootfs/usr/local/bin` with mode 0755 before writing the wrapper. Immediately afterward it syntax-checks the wrapper, proves executable mode and verifies that the launcher executes `/opt/opi/apps/moonlight/moonlight-qt`.

The static generated-payload audit now includes both rootfs customization fragments and artifact recipes. It validates 50 embedded shell/config payloads. Any literal `cat` redirection from a recipe into `/out/rootfs` is rejected unless an earlier `install -d` or `mkdir -p` explicitly initializes the destination parent. This turns the V3.15 failure class into an early repository-check failure.

## Warning classification

The log contains no earlier fatal compiler, linker, package or source-resolution error. The three `not found` configuration results are optional: FreeImage in ES-DE, Google Mock tests in PPSSPP and the BSD-only `elf_aux_info` libc probe. The build selected supported fallbacks or disabled tests.

Compiler warnings are confined to pinned upstream code and completed targets: FFmpeg/libmpv optimization diagnostics, bundled emulator/glslang warnings, and Moonlight use of a deprecated FFmpeg `AVCodec::pix_fmts` field. Package-manager man-page alternatives warnings are caused by `--no-install-recommends` build containers. None changed the terminal result or bypassed a mandatory gate. They remain useful upstream-maintenance signals but are not repaired locally because broad source edits would increase divergence from immutable releases without fixing this build.

## Requirements retained

Native Stremio remains mandatory; a UI-only or software-decoded result is a failure. Hardware acceptance still requires real H.264, HEVC 8-bit, HEVC Main10/HDR10, VP9 and AV1 decoding, including the 4K probes, plus affirmative Stremio process evidence. Moonlight also requires a real 3840×2160 session with affirmative hardware-decoder evidence.

The EasySMX X20, wired/2.4 GHz/Bluetooth controller coverage, HDMI/DisplayPort and Bluetooth audio, Panthor/PanVK, controller-first Gamescope/ES-DE session, Labwc fallback and 4 GB thermal/memory soak gates remain unchanged. Steam is experimental and cannot block stable-image acceptance.

NVMe policy remains read-only until the image is finalized. The image may inventory the drive and read SMART data only. After approval, Armbian's interactive `armbian-install` is the intended route for SD boot plus NVMe root. Later eMMC installation can replace SD boot and permit SD removal.

## Boundary of this audit

This audit proves repository consistency and interprets the completed host-build evidence. It cannot substitute for the next fresh host build or physical Orange Pi tests. V3.16 is ready for that build; it is not yet a known-good release image.
