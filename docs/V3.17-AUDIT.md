# V3.17 intensive whole-image audit

## Evidence reviewed

The V3.10 through V3.15 failure history and the complete attached build logs were reviewed through their terminal commands. The progression is internally consistent:

- V3.10 stopped because the isolated `gamepad-osk` build lacked a C compiler.
- V3.11 passed that point and exposed the legacy Snes9x/CMake policy issue.
- V3.12 passed CMake configuration and exposed Stremio's dedicated `libmpv` link-directory mismatch.
- V3.13/V3.14 corrected and proved the pinned FFmpeg, mpv/libmpv and native Stremio chain, then exposed Snes9x's GCC 15 `<cstdint>` incompatibility.
- V3.15 proved the Snes9x repair, built the major native artifacts, linked Moonlight to the dedicated media stack and stopped only because the Moonlight launcher destination directory did not exist.
- V3.16 explicitly creates and validates that directory and launcher. No evidence indicates a remaining compiler or source-compatibility failure before that point.

Static validation cannot guarantee a successful external network fetch or replace an ARM64 image build, but V3.17 moves newly introduced repository/package risk into early preflights so it fails before the multi-hour native build stage.

## Media decision

Native Stremio remains mandatory. Lumera is not a drop-in native Linux alternative: its ARM64 target is Android/Bionic, its player path is Android Media3/ExoPlayer, and using it would require an Android container plus RK3588 Android graphics and codec-HAL integration. That creates a second, unproven platform and hardware-decoding path on a 4 GB device. Stremio already compiles natively for the image and is forced to the pinned V4L2 Request FFmpeg/libmpv path. The release gate continues to require both standalone codec probes and evidence from actual Stremio playback; a working UI with software decode is a failure.

## Build-order and reproducibility audit

- Every attempt uses a fresh versioned Armbian workspace.
- High-risk Snes9x and Stremio builds remain early in native compilation.
- Git sources resolve to commits and completed native artifacts are checked against the source lock.
- Browser signing keys use pinned official fingerprints. Brave and Firefox install in an isolated ARM64 Ubuntu 26.04 container before native artifact compilation, and final package architecture is checked again in the target root.
- Generated shell, JSON, XML and TOML payloads are parsed before image creation. Recipe redirects into the image overlay require a pre-created parent directory.
- Final target-root and read-only offline-image gates independently assert critical executables, services, browser policy, media linkage, kernel configuration and forbidden legacy packages.
- Network Git operations remain non-interactive and bounded by time/low-speed limits.

## Display, graphics and streaming audit

Gamescope does not force a physical output size, leaving output-mode selection to the display/compositor. Immediately before Moonlight starts, `opi-moonlight-display-auto` reads the active Wayland output, selects its current mode (preferred/highest fallback), records resolution and refresh, examines the matching connector EDID for HDR static metadata, and updates Moonlight. A safe 1280×720/60 SDR configuration remains if detection fails. Moonlight hardware decode remains forced and linked to the dedicated media libraries. The session gate requires the exact detected resolution and affirmative hardware-decoder evidence; therefore a connected 4K display still imposes a real 4K validation.

The Panthor/PanVK and Rockchip DRM/media kernel requirements remain explicit. Performance governors are forced where available. The 4 GB policy retains zram, low-priority disk swap and earlyoom while avoiding needless full desktop components. The Geekworm 515 fan and sustained temperatures still require physical validation because the image cannot prove board-specific cooling behavior offline.

## Controller, session and user-interface audit

- greetd starts Gamescope and ES-DE; exiting or failing Gamescope falls back to Labwc.
- Any device marked `ID_INPUT_JOYSTICK=1` is accepted by the native Linux-input check. The EasySMX X20 remains the required three-transport reference test.
- `gamepad-osk` runs in both gaming and desktop sessions. Guide+Start toggles the OSK; its existing right-stick cursor/button mouse mapping is retained for non-native controller UIs such as browsers.
- ES-DE entries expose Stremio, Moonlight, Brave, Firefox, Steam experimental, network, audio, Labwc desktop, gaming-session restart, reboot and power-off.
- Brave is the default browser; Firefox remains an alternative. Both use Wayland-capable launchers and the controller mouse/OSK rather than claiming unsupported native browser gamepad navigation.
- OpenCode remains installed. Kodi, RetroArch/libretro, XFCE and LightDM remain excluded.

## Audio, wireless, locale and security audit

PipeWire/WirePlumber supports HDMI/DisplayPort and Bluetooth audio. HDMI is not hard-locked: it is the expected initial default when present, while the user can select Bluetooth through the ES-DE audio entry or desktop panel. NetworkManager and Blueman expose Wi-Fi, Bluetooth audio and Bluetooth keyboard/mouse setup. UK locale, keyboard, timezone and regulatory domain are explicit and gated. Security-only unattended upgrades are enabled, automatic reboot is disabled, SSH remains disabled by default, and broad passwordless sudo is not introduced.

## Storage audit

During image development, the NVMe helper performs only `lsblk` inventory and `nvme smart-log`; repository gates prohibit partitioning and formatting commands. The intended post-approval topology is:

1. validate the complete image while booting and running from SD;
2. use interactive `armbian-install` to retain SD boot while moving root to Btrfs on NVMe;
3. re-run all release gates on NVMe root;
4. when eMMC is installed, move boot to eMMC while retaining the NVMe root;
5. prove cold boot before removing SD.

The kernel and userspace cover Btrfs, Ext-family, exFAT, NTFS and FAT removable media. The swapfile helper detects Btrfs, rejects an invalid copied swapfile, and recreates it with copy-on-write and compression disabled before `mkswap`.

## Remaining physical release gates

V3.17 is ready to build, not declared final. Final status requires all of the following on the Orange Pi 5 Pro:

- repeatable cold boot and display auto-detection across available displays;
- Panthor/PanVK acceleration and stable 1080p60-oriented emulator behavior;
- native Stremio H.264, HEVC 8-bit, HEVC Main10/HDR10, VP9 and AV1 hardware decoding, including visible 4K probes and actual-process evidence;
- Moonlight hardware decoding at the detected display mode, including 4K/HDR when detected;
- representative content in every emulator family, controller navigation, BIOS handling, ES-DE scraping and RetroAchievements where supported;
- EasySMX X20 wired, 2.4 GHz and Bluetooth, plus any additional available controllers;
- HDMI and Bluetooth audio, Wi-Fi, Bluetooth keyboards/mice and HDMI-CEC;
- Brave and Firefox through controller mouse/OSK;
- Labwc fallback, network/audio/power entries, OpenCode and visible experimental Steam;
- 4 GB memory pressure, maximum-performance governor behavior, Geekworm 515 fan operation and sustained thermal soak;
- `opi-validation-report` with zero failures.

Only after those pass may NVMe migration begin. NVMe success is then validated separately before the image is called stable.
