## Conclusion

V3.23 correctly made PPSSPP's GLEW dependency explicit, but that package-specific repair did not by itself eliminate the mechanism behind the project's repeated late runtime-library failures. V3.24 changes the package pipeline so a successful pre-Armbian ELF closure becomes the source of an explicit, persisted package contract. This is intended to move the entire class of missing-system-library failures ahead of the long Armbian kernel/image phase.

The repository is statically ready for a fresh V3.24 build. A completed build and physical Orange Pi 5 Pro validation remain necessary; no source-only audit can prove board graphics, video decode, controllers, displays, audio, wireless or thermals.

## Failure pattern

Recent builds compiled applications successfully inside isolated development environments and then stopped in final target validation because a runtime package was absent. The recurring pattern was:

1. a development package supplied both headers and its runtime library in the artifact container;
2. the artifact linked successfully;
3. generic runtime inference or a hand-maintained manifest did not retain the runtime owner strongly enough;
4. the clean pre-Armbian container happened to receive the library through another package's dependency closure;
5. Armbian's populated root selected a different valid dependency solution;
6. the final `ldd` gate found the missing SONAME after the expensive kernel/rootfs work.

The final gate behaved correctly, but the earlier gate proved availability rather than reproducibility.

## V3.24 package-contract flow

| Step | Fail-closed behavior |
|---|---|
| Artifact build | Every native artifact must produce a nonempty, syntactically valid runtime-package manifest |
| Generic collection | Every resolved system library under `/lib` or `/usr/lib` must map to a dpkg owner; canonical merged-`/usr` paths and multiarch owner suffixes are handled |
| Clean ARM64 closure | Core native applications resolve only through the project media prefix and system libraries; each extracted AppImage resolves separately through only its own bundled-library path |
| Owner derivation | The closure stage scans all custom runtime trees and records every system package that owns a resolved library |
| Final manifest | Derived owners are merged into `required-packages.txt` before the final Resolute solver and before Armbian starts |
| Target root | Every entry in the generated manifest must have `install ok installed` status, in addition to named critical package and SONAME checks |
| Raw image | Read-only offline QA parses the final dpkg database and proves the complete generated manifest survived image assembly |

This deliberately allows the final contract to contain fundamental packages such as the C/C++ runtime when custom ELF files resolve through them. Redundant explicit installation is inexpensive; relying on an accidental dependency after a multi-hour build is not.

## Regression evidence

The static test suite includes an executable fixture for the exact merged-`/usr` and multiarch case: `ldd` reports `/lib/aarch64-linux-gnu/libGLEW.so.2.2`, canonicalization produces the dpkg-owned `/usr/lib/aarch64-linux-gnu/libGLEW.so.2.2.0`, and the collector must emit `libglew2.2` rather than `libglew2.2:arm64` or nothing. A second fixture makes the system library owner unavailable and requires the collector to fail.

Existing gates remain in place for PPSSPP/GLEW, Moonlight's SDL2_ttf and Qt Quick Controls, gamepad-osk's SDL3/SDL3_ttf, PanVK, board firmware, AppImage launchers, source locks, generated scripts/configuration, kernel symbols, browsers, services and the dedicated Stremio/Moonlight media prefix.

Core, DuckStation and ARMSX2 closure paths are deliberately isolated. Without that separation, a library bundled by one application could mask a missing dependency in another during the early scan even though the final launcher does not expose the unrelated library path.

## Remaining physical gates

After a successful image build, acceptance still requires real-board proof of the controller-first Gamescope/ES-DE session, Labwc desktop, native emulators, broad Linux controller input, the EasySMX X20 reference transports, controller mouse/OSK, display mode and HDR selection, HDMI and Bluetooth audio, CEC input, Wi-Fi/Bluetooth firmware, Panthor/PanVK, Moonlight hardware decode and Stremio-originated V4L2 Request decoding for the required codecs and 4K cases.

The installed NVMe remains read-only during development. Following final approval, the planned storage state is SD boot with Btrfs root on NVMe, then eMMC boot with the same NVMe root after eMMC installation and cold-boot validation.
